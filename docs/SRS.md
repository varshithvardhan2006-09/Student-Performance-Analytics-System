## 1. Introduction

### 1.1 Purpose

This document specifies the requirements for the **Student Performance Analytics System (SAPS)**,
a web application that lets a teacher upload a class mark sheet and receive validated,
computed performance analytics together with AI-generated commentary and downloadable reports.

It is written for the project's evaluators, for any developer maintaining the codebase, and
for the author's own reference during the viva.

### 1.2 Scope

SAPS covers the full path from a raw mark sheet to a decision a teacher can act on:

* ingestion of CSV, XLSX/XLS and structured PDF mark sheets,
* verification that the uploaded file really is the type it claims to be,
* validation of every record with a specific, per-row error message,
* computation of class-level and per-student analytics,
* natural-language insight generation and a question/answer interface over the uploaded data,
* export of the results as PDF, Excel or CSV,
* a per-teacher history of every upload, with cascade deletion.

SAPS is **single-role**: every account is a teacher. There is no student login, no parent portal
and no institution-wide administration. Marks are analysed per upload; the system does not
attempt longitudinal tracking of an individual student across academic terms.

### 1.3 Definitions and abbreviations

| Term | Meaning |
|---|---|
| **Upload** | One mark sheet submitted by a teacher, and the unit that all analytics attach to |
| **Single-subject report** | A sheet with one `Marks` column |
| **Multi-subject report** | A sheet with one column per subject, averaged into an overall mark |
| **Analytics** | The 11-field computed summary stored per upload |
| **Insight** | Natural-language commentary generated by Groq, or by the local template fallback |
| **Magic bytes** | The leading byte signature that identifies a file's true format |
| **JWT** | JSON Web Token, the bearer credential issued at login |
| **SPA** | Single Page Application |

## 2. Overall description

### 2.1 Product perspective

SAPS is a self-contained three-tier application.

```
Teacher's browser          Node.js / Express 5              MongoDB
+------------------+       +----------------------+       +------------------+
| Vanilla JS SPA   | HTTPS | REST API, 18 routes  |       | 7 collections    |
| Chart.js         |<----->| JWT auth             |<----->| indexed per      |
| frontend/src/    | JSON  | parsing + analytics  |       | uploadId, userId |
+------------------+       +----------+-----------+       +------------------+
                                      |
                                      | HTTPS (optional)
                                      v
                            +---------------------+
                            | Groq API            |
                            | llama-3.1-8b-instant|
                            +---------------------+
```

The Groq dependency is **optional by design**. When `GROQ_API_KEY` is absent, the AI service
falls back to locally generated template insights and every other feature works unchanged.

### 2.2 Product functions

| # | Function |
|---|---|
| 1 | Teacher registration and authentication |
| 2 | Multi-format mark sheet upload with format verification |
| 3 | Flexible column-header detection |
| 4 | Record validation with per-row diagnostics |
| 5 | Analytics computation (class and per-student) |
| 6 | Interactive dashboard with subject and student filters |
| 7 | Paginated, searchable student table |
| 8 | AI insight generation and AI question answering |
| 9 | PDF / Excel / CSV report export |
| 10 | Upload history with cascade delete |
| 11 | Teacher profile and usage statistics |

### 2.3 User characteristics

The single user class is a **school or college teacher**. Assumed skills: able to use a web
browser and to export a mark sheet from Excel or their institution's portal. No programming,
statistics or database knowledge is assumed, so all error messages name the offending row and
column in plain language.

### 2.4 Operating environment

| Component | Requirement |
|---|---|
| Client | Any modern browser with ES module support (Chrome/Edge 91+, Firefox 89+, Safari 15+) |
| Server | Node.js 18+ (developed and tested on Node.js 22) |
| Database | MongoDB 5.0+ (local `mongod` or MongoDB Atlas) |
| Deployment | Backend serves frontend in development; any Node host for production |

### 2.5 Design and implementation constraints

* **No frontend build step.** The SPA is plain ES modules served as-is, requiring no bundler.
* **MongoDB native driver, not an ODM.** Schema is enforced in the validation service rather
  than by Mongoose, keeping the dependency list small and the validation logic testable.
* **In-memory rate limiting.** Correct for a single instance; a shared store would be required
  before running multiple replicas.
* **Secrets never in source.** All secrets and deployment origins come from environment
  variables; `backend/.env.example` documents every variable.

### 2.6 Assumptions and dependencies

* The uploaded sheet has a header row and one record per student.
* Roll numbers are unique within a single upload.
* The default passing threshold is 40% of the maximum marks unless the teacher overrides it.
* Groq availability affects only the wording of insights, never the numbers.

## 3. Functional requirements

Priority: **H** = must have, **M** = should have, **L** = nice to have.

### 3.1 Authentication and account management

| ID | Requirement | Priority | Endpoint |
|---|---|---|---|
| **FR-001** | The system shall allow a teacher to register with full name, email and password. The email shall be validated for format and rejected if already registered. Passwords shall be stored only as a bcrypt hash (cost factor 12). | H | `POST /api/signup` |
| **FR-002** | The system shall authenticate a teacher by email and password and return a signed JWT valid for 7 days. | H | `POST /api/login` |
| **FR-003** | The system shall reject any request to a protected route that does not carry a valid, unexpired bearer token, and shall distinguish "expired" from "invalid" in the error message. | H | all protected routes |
| **FR-004** | The system shall return the authenticated teacher's profile. | M | `GET /api/profile` |
| **FR-005** | The system shall return usage statistics for the authenticated teacher: total uploads, total students analysed, total reports generated. | M | `GET /api/profile/stats` |
| **FR-006** | The system shall create a demo teacher account at startup so the application can be evaluated without registering. | L | startup seed |

### 3.2 File upload and ingestion

| ID | Requirement | Priority | Endpoint |
|---|---|---|---|
| **FR-007** | The system shall accept mark sheets in CSV, XLSX, XLS and PDF format, up to 10 MB per file. | H | `POST /api/upload` |
| **FR-008** | The system shall verify the leading byte signature of every uploaded file and reject a file whose real format does not match its extension (for example a text file renamed to `.pdf`). | H | `POST /api/upload` |
| **FR-009** | The system shall detect column headers flexibly, treating `Roll No`, `ROLLNO`, `roll_no` and `Roll Number` as the same field, and likewise for student name and marks. | H | `POST /api/upload` |
| **FR-010** | The system shall support both single-subject sheets (one `Marks` column) and multi-subject sheets (one column per subject), detecting the type automatically. | H | `POST /api/upload` |
| **FR-011** | The system shall validate every record and reject the upload with a list of specific errors naming the row number and the problem: non-numeric marks, negative marks, marks above the maximum, duplicate roll numbers, missing required columns, empty file. | H | `POST /api/upload` |

### 3.3 Analytics

| ID | Requirement | Priority | Endpoint |
|---|---|---|---|
| **FR-012** | The system shall compute, for each upload: total / passed / failed student counts, average, highest and lowest marks, pass and fail percentages, a five-band marks distribution, the report type, and a per-subject summary for multi-subject uploads. | H | `POST /api/upload` |
| **FR-013** | The system shall rank students by marks and classify each into a performance category (Top Performer, Average Performer, Weak Student, Failed). | H | `POST /api/upload` |
| **FR-014** | The system shall return the stored analytics for an upload, and a filtered variant recomputed for a chosen subject and/or student. | H | `GET /api/analytics/:uploadId`, `GET /api/analytics/:uploadId/filtered` |
| **FR-015** | The system shall return the student table for an upload with pagination and with search, status, category and mark-range filters. | H | `GET /api/students/:uploadId` |

### 3.4 AI insights

| ID | Requirement | Priority | Endpoint |
|---|---|---|---|
| **FR-016** | The system shall generate natural-language insights for an upload using Groq (`llama-3.1-8b-instant`), persist them, and return locally generated template insights instead whenever no API key is configured or the API call fails. | H | `POST /api/ai-insights/:uploadId`, `GET /api/ai-insights/:uploadId` |
| **FR-017** | The system shall answer a teacher's free-text question about a specific upload, answering from the stored data where possible and declining questions unrelated to the uploaded marks. | M | `POST /api/ai-query/:uploadId` |

### 3.5 Reporting and history

| ID | Requirement | Priority | Endpoint |
|---|---|---|---|
| **FR-018** | The system shall export an upload's results as a multi-section PDF, an Excel workbook, or a CSV file, and shall record every export in the `reports` collection. | H | `GET /api/reports/:uploadId/{pdf,excel,csv}` |
| **FR-019** | The system shall list a teacher's uploads with pagination, newest first, and return the detail of a single upload. | M | `GET /api/uploads`, `GET /api/uploads/:id` |
| **FR-020** | The system shall delete an upload together with all of its students, analytics, AI insights and report records. | M | `DELETE /api/uploads/:id` |
| **FR-021** | The system shall expose an unauthenticated health endpoint reporting database connectivity, demo account presence and AI configuration status. | L | `GET /api/health` |

## 4. Non-functional requirements

### 4.1 Performance

| ID | Requirement |
|---|---|
| **NFR-P1** | A 500-record CSV shall be parsed, validated, analysed and persisted within 5 seconds on a local MongoDB instance. |
| **NFR-P2** | The student table shall be paginated server-side; the client shall never request more than 500 rows in a single call. |
| **NFR-P3** | Every collection queried on a request path shall be covered by an index — `uploads(userId, uploadDate)`, `students(uploadId, status, category)`, `analytics(uploadId)` unique, `users(emailKey)` unique. |
| **NFR-P4** | Uploaded files shall be held in memory and never written to disk, so no temporary-file cleanup is required. |

### 4.2 Security

| ID | Requirement |
|---|---|
| **NFR-S1** | Passwords shall be stored only as bcrypt hashes with cost factor 12. Plaintext passwords shall never be logged or returned. |
| **NFR-S2** | `JWT_SECRET` shall be at least 32 characters and shall be rejected at startup in production if weak or absent. |
| **NFR-S3** | CORS shall use an explicit origin whitelist built from configuration. Wildcard origins and hardcoded deployment URLs are prohibited. |
| **NFR-S4** | Authentication endpoints shall be rate limited (25 requests / 15 min / IP) and upload endpoints separately (30 requests / 15 min / IP). |
| **NFR-S5** | Every response shall carry `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, a `Referrer-Policy` and a `Permissions-Policy`. `X-Powered-By` shall be disabled. |
| **NFR-S6** | All user-supplied strings shall pass through `escapeHtml()` before being inserted into the DOM. |
| **NFR-S7** | Every document shall carry the owning `userId`, and every query shall filter by it, so one teacher can never read another's data. |
| **NFR-S8** | No secret shall appear in the repository. `.env` is git-ignored; `.env.example` documents the variables with placeholder values. |

### 4.3 Reliability and availability

| ID | Requirement |
|---|---|
| **NFR-R1** | The application shall remain fully functional when the Groq API is unreachable or unconfigured. |
| **NFR-R2** | The dashboard shall fall back to numeric tables with an explanatory message if the Chart.js CDN cannot be reached. |
| **NFR-R3** | In development the server shall auto-start a local `mongod` if one is not already listening. |
| **NFR-R4** | A failed upload shall leave no partial data: analytics and student rows are written only after validation succeeds. |
| **NFR-R5** | The server shall shut down gracefully on SIGINT/SIGTERM, closing the HTTP server and the MongoDB client. |

### 4.4 Usability

| ID | Requirement |
|---|---|
| **NFR-U1** | Validation errors shall name the row number and the specific problem, never a generic "invalid file". |
| **NFR-U2** | Any view awaiting a network round-trip shall display a loading skeleton rather than an empty area. |
| **NFR-U3** | The interface shall be responsive from 360 px upward. |
| **NFR-U4** | Progress indication during upload shall never claim completion before the server confirms it. |

### 4.5 Maintainability

| ID | Requirement |
|---|---|
| **NFR-M1** | No source file shall exceed roughly 700 lines; each module shall have a single responsibility. |
| **NFR-M2** | The analytics and validation services shall be importable and unit-testable without starting Express or MongoDB. |
| **NFR-M3** | `npm test` shall run the unit test suite using Node's built-in test runner, with no additional test dependency. |

### 4.6 Portability

| ID | Requirement |
|---|---|
| **NFR-PO1** | The frontend shall run without a build step so it can be served directly by the backend. |
| **NFR-PO2** | The backend shall run as a long-lived Node process on any Node host. |
| **NFR-PO3** | The API base URL shall be configurable, never hardcoded in committed source. |

## 5. Interface requirements

### 5.1 User interfaces

Seven views, all rendered by the SPA shell (`frontend/src/shell.js`):

| View | Purpose |
|---|---|
| Auth | Login and signup, with a demo account hint |
| Upload | File selection, subject name, maximum and passing marks |
| Processing | Stage-by-stage progress while the server analyses the file |
| Dashboard | Summary cards, charts, subject/student filters, student table |
| Insights | AI commentary and the free-text question box |
| History | Every past upload, with view / download / delete actions |
| Profile | Teacher details and usage statistics |

### 5.2 Software interfaces

| Interface | Direction | Protocol |
|---|---|---|
| Browser SPA to API | outbound | HTTPS, JSON, `Authorization: Bearer <jwt>` |
| API to MongoDB | outbound | MongoDB wire protocol via the native driver |
| API to Groq | outbound | HTTPS, chat completions, `llama-3.1-8b-instant` |

### 5.3 API summary

All 18 endpoints require authentication except `GET /api/health`, `POST /api/signup` and
`POST /api/login`.

| Method | Route | Auth | Purpose |
|---|---|---|---|
| GET | `/api/health` | no | Database, demo account and AI status |
| POST | `/api/signup` | no | Register a teacher |
| POST | `/api/login` | no | Authenticate, return JWT |
| GET | `/api/profile` | yes | Current teacher profile |
| GET | `/api/profile/stats` | yes | Upload / student / report counts |
| POST | `/api/upload` | yes | Ingest, validate, analyse, persist a mark sheet |
| GET | `/api/analytics/:uploadId` | yes | Stored analytics |
| GET | `/api/analytics/:uploadId/filtered` | yes | Analytics recomputed for a filter |
| GET | `/api/students/:uploadId` | yes | Paginated, filtered student table |
| POST | `/api/ai-insights/:uploadId` | yes | Generate and persist insights |
| GET | `/api/ai-insights/:uploadId` | yes | Fetch stored insights |
| POST | `/api/ai-query/:uploadId` | yes | Answer a question about this upload |
| GET | `/api/reports/:uploadId/pdf` | yes | Download the PDF report |
| GET | `/api/reports/:uploadId/excel` | yes | Download the Excel report |
| GET | `/api/reports/:uploadId/csv` | yes | Download the CSV report |
| GET | `/api/uploads` | yes | Paginated upload history |
| GET | `/api/uploads/:id` | yes | Single upload detail |
| DELETE | `/api/uploads/:id` | yes | Delete an upload and all child documents |

Every response uses the same envelope:

```json
{ "success": true,  "data": { } }
{ "success": false, "message": "Human-readable reason", "errors": ["Row 4: Marks cannot be negative (got -5)"] }
```

## 6. System architecture

### 6.1 Backend module structure

```
backend/
  index.js                    entry point: wiring and startup only (~180 lines)
  src/
    config/env.js             .env loading, configuration constants, startup validation
    db/connection.js          MongoDB connection, index creation, demo seeding, role migration
    middleware/
      security.js             security response headers
      cors.js                 configuration-driven origin whitelist
      rateLimiter.js          sliding-window limiter factory + the two limiter instances
      auth.js                 JWT verification
      upload.js               multer memory storage, 10 MB limit, extension filter
    services/
      fileParser.js           CSV / XLSX / PDF parsing and record normalisation
      validation.js           validateRecords() - per-row diagnostics
      analytics.js            calculateAnalytics(), processStudents(), filtered variants
      aiService.js            Groq integration, template fallback, question scoping
    routes/                   one Express Router per resource (8 files, 18 endpoints)
    utils/
      validators.js           isValidEmail, getFileSignatureError, escapeCsvValue, ...
      normalizers.js          header, report-type, marks and role normalisation
  tests/
    analytics.test.js         analytics engine unit tests
    validation.test.js        validation and helper unit tests
```

### 6.2 Frontend module structure

```
frontend/
  index.html                  static shell, loads script.js as an ES module
  style.css
  site-config.js              API base URL configuration
  script.js                   entry point: imports and initializeApp() (~210 lines)
  src/
    constants.js              storage keys, per-view page metadata
    state.js                  the single shared mutable state object
    dom.js                    cached shell element references
    api/config.js             API base URL resolution with fallbacks
    api/client.js             requestJson(), requestBlob(), auth headers
    utils/format.js           escapeHtml(), date and percentage formatting
    selectors.js              derived read-only views over state
    shell.js                  view routing, sidebar, page dispatch, loading skeleton
    charts/renderer.js        all Chart.js rendering plus the CDN fallback
    pages/                    auth, upload, processing, dashboard, insights, history,
                              profile, reports - one module per view
```

### 6.3 Upload processing pipeline

```
file  ->  extension filter (multer)
      ->  magic-byte check (getFileSignatureError)
      ->  format-specific parse (parseCSV | parseExcel | parsePDF)
      ->  header normalisation (normalizeColumnName)
      ->  record validation (validateRecords)      -- rejects here with row-level errors
      ->  student processing + ranking (processStudents)
      ->  analytics computation (calculateAnalytics)
      ->  persist: uploads, students, analytics
      ->  respond with uploadId
```

## 7. Data model

Seven MongoDB collections. Every document except `users` carries `userId` for isolation.

| Collection | Key fields | Indexes |
|---|---|---|
| `users` | `_id`, `fullName`, `email`, `emailKey`, `passwordHash`, `role`, `createdAt` | `emailKey` unique, `email` |
| `uploads` | `_id`, `userId`, `fileName`, `subjectName`, `reportType`, `maxMarks`, `passingMarks`, `status`, `uploadDate` | `userId`; `userId, uploadDate`; `userId, subjectName` |
| `students` | `_id`, `uploadId`, `userId`, `rollNo`, `studentName`, `marks`, `percentage`, `status`, `category`, `rank`, `subjectMarks` | `uploadId`; `userId, uploadId`; `uploadId, rollNo`; `uploadId, studentName`; `userId, rollNo` |
| `analytics` | `_id`, `uploadId`, `userId`, plus the 11 computed fields | `uploadId` unique |
| `aiInsights` | `_id`, `uploadId`, `userId`, `content`, `generatedAt` | `uploadId`; `uploadId, userId` |
| `reports` | `_id`, `userId`, `uploadId`, `format`, `createdAt` | `userId, createdAt` |
| `subjects` | `_id`, `userId`, `name` | — |

Referential integrity is maintained in application code: `DELETE /api/uploads/:id` removes the
upload's students, analytics, insights and report records in the same request.

## 9. Assumptions, constraints and future scope

### 9.1 Known constraints

| Constraint | Consequence |
|---|---|
| Rate limiter state is in process memory | Limits are per instance; a shared store is needed before horizontal scaling |
| Upload progress is a client-side estimate | The bar reflects elapsed time, not server progress, and is capped at 95% until the response arrives |
| Marks are analysed per upload | No longitudinal tracking of a student across terms |
| PDF ingestion depends on text extraction | Scanned image-only PDFs cannot be parsed; OCR is out of scope |

### 9.2 Future scope

* Server-sent events for genuine upload progress.
* Longitudinal student tracking across uploads and terms.
* Role-based access control now that role values are normalised (`normalizeRole()`).
* A shared rate-limit store to allow multiple backend instances.
* OCR for scanned PDF mark sheets.
* Bulk export of several uploads in a single archive.
